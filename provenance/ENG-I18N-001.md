# ENG-I18N-001 — MAM-836

Date: 2026-10-23. First coherent phase, based on origin/main 4e4d46f.

The embedded engine-api catalog is the sole production source for English (en,
default), Spanish (es) and Portuguese (pt) stable-code messages. CLI, Python and
WASM delegate language parsing, explanation lookup and diagnostic localization to
engine-api. Language identifiers are exact lowercase en/es/pt; selection never
uses LANG, LC_ALL or the system locale. No dependencies or external sources were
added. Published JSON keys, stable codes, messageKey, statuses and exit codes are
preserved; schemas are unchanged.

The task estimate was 31 + 14 + 23 keys per language. The actual existing English
error catalog and frozen CLI registry both contain **32**, including all nine
CLI and nine API codes plus fourteen ENG codes. Keeping every registered code
requires **32 errors + 14 diagnostics + 23 explanations = 69 keys per language**
(207 entries total). No existing entry was dropped to match the estimate.

Spanish and Portuguese translations were generated by Codex (gpt-6.1-sol high)
from the English catalog text, WITHOUT external sources. Native-speaker review
is PENDING, especially for Portuguese. Technical identifiers, field/method names,
codes, constants, numbers and mathematical notation are preserved. Tests require
complete, equal key sets, English compatibility, nonempty trimmed translations,
translated es/pt entries (no untranslated exceptions), and technical markers.
English explanations are checked against engine_core::catalog and the historical
API explanation function retained only as a test reference.

Phase 1 translates errors.<code>, explain.<code>, and only diagnostics whose
cause exactly equals the English default message for their ENG code. Specific or
parameterized causes and every hint stay unchanged. English document localization
returns the original bytes without serialization. Python run failures retain the
localized cause, diagnostics and document. WASM accepts a final optional lang;
Python validates facade language arguments before FFI. CLI supports --lang as a
separate global option alongside --timeout, preserving SDK flag values.
The new describe flag description follows its existing Spanish neighbors; the
language of describe/help is otherwise unchanged in this phase.

Jonathan's mandatory decision (option a): workflow recordFingerprint and SDK step
input/output fingerprints exclude message text. EngineMethod returns a fingerprint
view with cause and hint removed from each diagnostics entry; codes, severity,
entities and all numeric/context data remain. The complete localized document is
retained in state.results and published as engineResults. Consequently the sealed
record does **not** attest to message wording. This intentional fingerprint change
also applies to English; other English outputs retain their existing bytes except
for the added describe flag. Input fingerprints remain unchanged. Vendor code is
untouched.

The manifest regression uses a successful run with the real
API-W-COMBINED-PRESCRIBED warning: invalid models terminate with cli-error/1 and
cannot supply a successful workflow manifest. That specific API warning remains
English in phase 1. A separate fingerprint-view test changes both cause and hint
across all three languages and verifies that only message text is excluded.
Real broken-reference fixtures verify translated ENG causes in API, CLI, WASM and
Python; subprocess tests cover explicit language independence from host locales.
Native WASM tests cover successful exports and validate the invalid-language
parser plus the ApiError serialization used by the JS boundary; constructing and
catching a thrown JsValue requires a JS/WASM runtime.

Phase 2 remains out of scope: approximately 900 parameterized messages, all hint
text, ApiError and input parsing messages, Python-owned PY-E-* and facade
validation messages, mcp/compile/methods language behavior, and describe/help
language. Default-language compatibility is preserved for these surfaces.

changes. Python syntax compilation passed; 37 unittest cases across test_i18n,
